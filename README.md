# Siginon Safety Hub — local copy

This is a local, standalone copy of the **Siginon Safety Hub** (SafeGuard) project,
pulled directly from its Lovable-hosted source files via the Lovable MCP connector,
after the Lovable workspace ran out of credits and couldn't apply further changes
through its own AI agent.

It connects to the **same live Supabase project** the Lovable app uses
(`xqxjyrswkqajpmswqmal`) — this is not a copy of the database, it's the same one.

## What's real and working

- **Database schema** — all 6 tables (`profiles`, `reports`, `attachments`,
  `sla_rules`, `status_log`, `comments`), triggers (auto reference numbers,
  SLA due dates, status audit log), and RLS policies. See `supabase/migrations/`.
- **Report submission form** (`src/routes/index.tsx`) — inserts real rows into
  `reports`, uploads photos to a real Supabase Storage bucket
  (`report-attachments`), inserts matching `attachments` rows, and remembers
  submitted reference numbers in `localStorage` so "Your recent reports" can
  look them up live.
- **Zone/site field** — a real dropdown backed by a `sites` table
  (`supabase/migrations/20260727000000_sites_table.sql`), populated with
  Siginon's actual site codes. No more free-text guessing. Adding a new site
  later is just an `insert into public.sites (name) values ('XYZ');` — no
  frontend change needed, it reads the list live.
- **Dashboard & Users pages** — all mock arrays (`reports`, `typeMix`,
  `zoneData`, `trendData`, `seedUsers`, etc.) have been replaced with live
  Supabase queries, scoped by real RLS.
- **Staff authentication** (`src/lib/app-shell.tsx` → `useAuth()`) — real
  `supabase.auth.signInWithPassword()`, a live session via
  `supabase.auth.onAuthStateChange`, and role/name pulled from each user's
  `profiles` row. No more localStorage role picker.

## Getting your first staff accounts working

There's no self-serve signup or admin invite UI yet — accounts are seeded
manually for now (fastest path while other priorities firm up):

1. **Supabase Dashboard → Authentication → Users → Add user.** Create an
   account per staff member, with **"Auto Confirm User"** checked so they can
   sign in immediately without email verification.
2. **Supabase Dashboard → SQL Editor** — run
   `supabase/seed/seed_staff_profiles.sql` (edit the emails/names/departments
   to match who you actually created). This links each auth account to a
   role by inserting its matching `profiles` row.
3. Sign in at `/auth` with that email/password — the dashboard should now
   show real, role-scoped data.

If a real login succeeds but the dashboard still looks stuck ("Redirecting to
sign in…"), it almost always means step 2 was skipped — `useAuth()` treats
"session exists but no `profiles` row" as a distinct state
(`missingProfile`) rather than pretending they're signed out, but the UI
doesn't currently surface that message anywhere prominent yet.

**Still missing:** self-serve signup, an admin "invite user" flow, and
password reset. All three are natural next steps once you're ready to move
past manual seeding.

## Other known gaps / follow-ups

- **Corrective actions / comments UI** — the `comments` table exists and has
  RLS, but there's no UI wired to it yet.
- **Email notifications** — not part of this pass; that's the Edge Function +
  Database Webhook layer discussed separately, triggered on `assigned_to`
  changes.
- **Users page management actions** ("Invite user", role changes, suspend) —
  disabled in the UI for now since they need the real-auth flow above plus
  (for suspend) a schema column that doesn't exist yet.
- **Attachment photo tagging** — every upload is currently tagged
  `"supporting"` by default; the UI doesn't yet let a reporter tag individual
  photos as before/after.
- **Siginon logo** — Lovable's asset URL for the real logo only resolves
  inside Lovable's hosting, so a placeholder SVG (`public/siginon-logo-placeholder.svg`)
  stands in for it here. Drop your real logo file in `public/` and update the
  `src` reference in `src/assets/siginon-logo.png.asset.json` to swap it back in.

## Running it locally

```bash
npm install
npm run dev
```

Supabase connection details are already in `.env` (the anon/publishable key —
safe to be public, RLS enforces access). No further setup needed to view the
public report form; sign-in-gated pages will show an empty state until real
auth is wired per the section above.

**Note on `src/routeTree.gen.ts`:** this file is auto-generated by Vite from
the files in `src/routes/` and is intentionally gitignored — don't hand-edit
it. It only exists after `npm run dev` or `npm run build` has run at least
once, so running `tsc --noEmit` on a completely fresh checkout (before ever
running dev/build) will show a handful of errors about it being missing.
That's expected, not a bug — run `npm run dev` once first and the errors
disappear.

**Note on `vite.config.ts`:** only pass router options (routes directory,
generated route tree path) through `tanstackStart()`'s own `router` key.
Don't add a separate `tanstackRouter()` plugin alongside it — TanStack Start
already registers its own internal router plugin instance, and Vite doesn't
dedupe two plugins with the same name. Having both caused a
`Duplicate declaration "hot"` error specifically in `npm run dev` (not
`build`, since that error only fires during HMR injection).

**Note on `get_user_role()`:** an earlier migration revoked `EXECUTE` on this
function from `anon`/`authenticated`, intending to stop it being called
directly as an RPC. That broke every RLS policy that references it
internally (Postgres requires `EXECUTE` privilege to invoke a function even
from inside a policy's `USING` clause) — it surfaced as `401` errors on
`reports`/`status_log` queries. Fixed in
`20260724000000_fix_get_user_role.sql` by redefining it as a zero-argument
function (reads `auth.uid()` internally, so nothing sensitive to query even
if called directly) with `EXECUTE` properly granted.


## Structure

- `src/routes/` — pages (`index.tsx` = public report form, `dashboard.tsx` =
  staff dashboard, `users.tsx` = user directory, `auth.tsx` = sign-in)
- `src/lib/app-shell.tsx` — shared nav, footer, and the demo auth hook
- `src/integrations/supabase/` — Supabase client + generated types (matches
  the live schema exactly)
- `supabase/migrations/` — the SQL that was actually run against the live
  database, in order
- `src/components/ui/` — shadcn/ui primitives (only the ones actually used by
  the app pages are included here, not the full shadcn set)
